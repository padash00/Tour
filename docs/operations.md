# Эксплуатация F16 Arena

## Где смотреть состояние

`/admin/servers` показывает возраст последнего сигнала, очередь команд, версии и время обработки синхронизации.
Отдельно видны времена игровых таймеров и обслуживания. Если их последний запуск запаздывает,
проверьте `agent.log` и ошибки маршрута `/api/agent/jobs` в Vercel.
После 15 секунд без сигнала появляется задержка, после 30 — отсутствие связи.
Таймер продолжает работать даже без новых данных от агента. Время обработки — последнее измерение,
не среднее и не показатель задержки браузера. Подробности фоновых задач открываются под карточками.
Быстрая синхронизация принимает состояние и выдаёт команды. Игровые таймеры работают отдельным запросом
примерно раз в 5 секунд, обслуживание — раз в минуту. Блокировка в базе не допускает одновременный
запуск одинаковых задач при двух процессах агента.

Статусы команд: «В очереди» — агент ещё не получил; «Отправлено» — сайт передал команду;
«Выполнено» — агент подтвердил успех; «Ошибка» — получен отказ либо истёк срок ожидания.
Повторная доставка с тем же ID не запускает команду заново. Обычные команды ожидают результат до 3 минут,
обслуживание — до 45 минут. Поздний ответ не перезаписывает уже зафиксированную ошибку тайм-аута.

## Запуск агента

На серверном ПК с установленным CS2 Server агент запускается задачей Планировщика `F16 Server Agent`
после входа владельца ПК в Windows. Агент работает в его интерактивном сеансе: запуск от `SYSTEM`
вызывал падение `cs2.exe` в `tier0.dll`.
Задача `F16 Server Agent Watchdog` раз в минуту запускает агент вновь, если его процесс закрыли.
Перезапуск агента не включает выключенные через сайт игровые серверы.
Для намеренной остановки отключите задачу `F16 Server Agent` в Планировщике; сторож не включает
отключённую задачу. Для возобновления включите и запустите её.
Чтобы запустить остановленную задачу, откройте Планировщик и выберите «Выполнить».
Чтобы установить автозапуск, войдите под владельцем серверного ПК и в PowerShell администратора выполните:

```powershell
powershell -ExecutionPolicy Bypass -File D:\cs2server\f16\service.ps1
```

Агент работает без консольного окна. Для уже установленной задачи после обновления скриптов можно
в PowerShell администратора выполнить `service.ps1 -UpdateActionOnly`: действие задачи обновится без
остановки текущего агента, а при следующем запуске окно Node.js не появится.
После перезагрузки Windows агент с типом входа `Interactive` запустится только после входа владельца ПК.
Планировщик и сторож не заменяют включение ПК и вход пользователя. Запуск CS2 от `SYSTEM` ранее падал;
перед изменением типа входа нужна проверка на свободном инстансе, иначе можно оставить матчи без сервера.

При другом пути установки измените команду. После появления «На связи» управление CS2 доступно на сайте.
Выключенный ПК или неработающий агент требуют локального запуска; сайт не может исполнить команду
на ПК без работающего получателя. Журнал: `D:\cs2server\f16\agent.log`.

Журнал команд `command-journal.json` хранится рядом с конфигом агента. Не удаляйте его при обновлении:
он предотвращает повторное исполнение и сохраняет недоставленные подтверждения.
Если процесс завершился во время команды, агент сообщает «результат неизвестен».
Проверьте реальное состояние сервера до ручного повторения. Повреждённый журнал останавливает запуск
агента; сохраните копию файла и изучите лог, прежде чем восстанавливать его из резервной копии.

## Если пропала связь

1. Проверьте питание ПК, интернет и задачу `F16 Server Agent`.
2. Откройте `agent.log`; проверьте адрес сайта и соответствие токена в конфиге окружению сайта.
3. После восстановления связи агент досылает события и результаты из дискового буфера.
4. Проверьте журнал команд и активный матч. Не перезапускайте CS2 только из-за красного индикатора связи.

## Целостность данных

- Заявка, выбранный состав и автоодобрение записываются одной SQL-транзакцией. Конфликт игрока откатывает всю замену состава.
- Одобрение блокирует строку турнира до проверки вместимости; правило действует и для административных действий.
- Назначение игрового сервера и создание команды загрузки происходят вместе. Лобби и турнирные матчи используют одну блокировку назначения.
- Ручной счёт карты, итог серии и удаление несыгранных карт записываются вместе. Обновление сетки запускается после фиксации результата.
- Пачка HTTP-лога сохраняет раунды, Swing, состояние разбора и отметку обработки одной транзакцией.
- События MatchZy имеют аренду обработки. Повтор во время работы получает 503 и остаётся в буфере агента;
  после аварии обработка доступна повторно через 2 минуты. Завершённые события подтверждаются без повторной обработки.
- Сетка плей-офф обновляется оптимистично: сайт считает изменения по снимку матчей, `sync_bracket_apply`
  под блокировкой турнира сверяет снимок и пишет все изменения разом. Если сетку успели изменить, ничего
  не пишется и сайт пересчитывает заново (до 5 попыток).
- Матчи новой стадии и отметка о ней (`bracket_published_at`, `playoff_created_at`, тур швейцарки) пишутся
  одной транзакцией `create_stage_matches`. Повтор или параллельный вызов ничего не создаёт; сбой не оставляет
  отметку без матчей.
- Завершение вето (карты серии и статус «готов») — `finish_veto` под блокировкой матча; таймер вето и ход
  капитана одновременно не задваивают карты.
- Вступление в команду (`join_team`) и передача капитанства (`transfer_team_captain`) блокируют строку команды.
- Ограничение частоты действий — `rate_limit_claim`: из двух одновременных запросов проходит один.
- CHECK-ограничения на матчи, карты и турниры и связь «игрок состава — турнир заявки». Если существующие
  строки нарушали новое ограничение, миграция не падает, а оставляет его `NOT VALID` (NOTICE в журнале):
  `select conname from pg_constraint where not convalidated;` — исправьте данные и выполните `validate constraint`.
- Публичных политик чтения нет: сайт работает только через `service_role`, RLS включён на всех таблицах.
- Очистка журналов: `select prune_old_rows();` удаляет `audit_logs` старше 180 дней, `match_events` старше 365,
  выполненные `agent_commands` старше 30 (параметры меняются, минимум 7 дней). Автоматически не запускается.
- RPC доступны только `service_role`. Проверка Steam-сессии и прав администратора остаётся в Server Actions.
  `p_admin` — доверенный параметр сервера после `requireAdmin`, он поддерживает и `ADMIN_STEAM_IDS`.

## Выпуск и восстановление

1. Выполните `npm ci`, `npm run check`, `npm test`, `npm run build`.
2. Проверьте наличие резервной копии базы и отсутствие активных матчей для изменений игровой логики.
3. Укажите `SUPABASE_PROJECT_REF` и `SUPABASE_ACCESS_TOKEN`, выполните `npm run db:migrate`, затем `npm run db:check`.
4. Отправьте код в `main`. Production-сборка проверит историю миграций через серверный ключ.
5. Проверьте `/admin/servers`, обновление версии агента и одну штатную команду на свободном резервном инстансе.

### Ограничения раннера миграций

`npm run db:migrate` (`scripts/lib/migrations.mjs`) выполняет каждый файл одной транзакцией: SQL файла
передаётся в `execute` внутри блока `DO` под общей advisory-блокировкой. Отсюда правила для новых миграций:

- Нельзя то, что запрещено внутри транзакции: `create index concurrently`, `vacuum`, `alter system`,
  `alter type … add value` с использованием нового значения в том же файле. Индекс на большой таблице
  создаётся обычным `create index` и блокирует запись на время построения — делайте это вне турнира.
- `begin`/`commit` в файле не пишутся: файл целиком либо применяется, либо откатывается.
- Применённый файл не редактируется: контрольная сумма (sha256 с нормализацией CRLF) сверяется раннером
  и production-сборкой (`scripts/check-deploy-schema.mjs`). Исправление — новой миграцией.
- Имя — `ГГГГММДДччммсс_описание.sql` (латиница в нижнем регистре, цифры, `_`); порядок применения — по имени.
- Новые ограничения на существующие данные добавляйте `NOT VALID` и проверяйте отдельным блоком с обработкой
  исключения, чтобы старые строки не сорвали выпуск.
- e2e/smoke-скрипты (`scripts/e2e-*`, `smoke-queries.mjs`) отказываются работать с размещённым проектом
  Supabase (это production); локальный стек разрешён, production — только с `E2E_ALLOW_PROD=1`.

При ошибке приложения откатите deployment Vercel. Добавочные таблицы/колонки/RPC сохраняйте:
удаление миграции из истории не откатывает схему. Для исправления схемы создавайте новую миграцию.
Перед восстановлением базы остановите новые заявки и назначение матчей; восстановите резервную копию
через Supabase и проверьте актуальность секретов окружения. Реальное восстановление базы и запуск CS2
не выполняются автоматическими offline-тестами.

## Проверки и известные ограничения

CI выполняет типы, ESLint, все offline-тесты и production build. Тесты миграций используют настоящий
PostgreSQL в памяти (PGlite), но только одно подключение. Для нагрузочной проверки блокировок нужен
отдельный PostgreSQL/Supabase staging с несколькими подключениями. Рабочие турниры не используйте как тестовые данные.

Supabase advisors на 05.10.2026: закрытые служебные таблицы имеют RLS без публичных политик — это намеренно.
Существующее расширение `citext` остаётся в `public`; перенос требует отдельной проверки зависимостей.
Добавлены индексы на используемые здесь запросы; все рекомендации по внешним ключам не применяются вслепую.
`npm audit` сообщает о 5 связанных предупреждениях в dev-цепочке ESLint → fast-glob → braces;
предлагаемый автоматический downgrade Next ESLint до 14-й версии не применён.

## Регион сайта и базы

`vercel.json` сейчас задаёт `syd1` (Сидней). Прежде чем менять регион, проверьте первичный регион
Supabase в панели проекта и измерьте задержку от серверного ПК до сайта, а также время запроса
сайта к базе. Перенос только Vercel при далёкой базе способен увеличить задержку. Регион базы
Supabase меняется через создание нового проекта и перенос данных, поэтому это отдельное изменение.
